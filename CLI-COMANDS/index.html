    Comandos CLI¶

    Referência dos comandos do projeto: a CLI do Fleven (atalhos do dia a dia) e a CLI do Flower (flwr e os binários flower-*, versão 1.31).

    Comece pela CLI do Fleven — é o que a equipe usa na maior parte do tempo. Os comandos do Flower aparecem depois, agrupados por tarefa.

    Fleven CLI¶

    Instalada com pip install -e ".[dev]". Cada comando embrulha um script em tools/.

    fleven setup¶

    Cria os junction points dos grupos em data/. Rode uma vez, antes do primeiro fleven run.

    fleven setup

    fleven run¶

    Roda os experimentos em lote: todas as combinações de grupo × modelo × estratégia.

    fleven run --only G01 G03 --strategies fedavg --model-types lstm

    Pula os que já terminaram

    Runs marcados como FINISHED no MLflow são ignorados. Use --no-skip-existing para forçar a re-execução e --no-eval para pular o relatório após cada run.

    fleven eval¶

    Gera o relatório de um experimento (PDF + CSV + resumo no terminal).

    fleven eval -e G01_HEV_18L_3000 -s fedyogi --no-pdf

    fleven explore¶

    Análise exploratória dos dados (EDA) por grupo.

    fleven explore --only G01 G03

    fleven push¶

    Sincroniza os runs locais do MLflow para o DagsHub, para compartilhar com a equipe.

    fleven push

    Credenciais

    Exige as variáveis DAGSHUB_USER e DAGSHUB_TOKEN (token em dagshub.com/user/settings/tokens).

    Flower¶

    O flwr run . roda a federação com atores Ray na sua máquina. Precisa do FLWR_HOME apontando para a config versionada do projeto (veja FLWR_HOME).

    flwr run¶

    Inicia o treino; --stream acompanha e espera terminar.

    $env:FLWR_HOME = "$PWD\.flwr"
flwr run . --federation-config "num_supernodes=14" --stream
    • --federation-config — número de clientes por run.
    • --run-config — sobrescreve hiperparâmetros da app:
    flwr run . --run-config "rounds=5 learning-rate=1e-4" --stream

    Hífen vs underscore (mesmo ajuste, superfícies diferentes)

    Como flag do comando flwr federation simulation-config, é com hífen (--num-supernodes, --client-resources-num-cpus), seguindo a convenção de flags. Mas dentro da string do --federation-config é com underscore (num_supernodes=..., client_resources_num_cpus=...). A doc do Flower mostra a forma de flag (hífen); na string, use underscore — senão dá invalid format.

    Acompanhar e listar runs¶

    flwr log <run-id> --stream         # anexa nos logs de um run já iniciado
flwr ls fleven-deployment          # lista os runs de um SuperLink
flwr stop <run-id> fleven-deployment   # para um run em execução
flwr pull <run-id> fleven-deployment   # baixa os artefatos (retorna uma URL)

    flwr ls recebe o nome da conexão, não a federação

    Use flwr ls fleven-deployment (nome da conexão do SuperLink), não flwr ls . <federação>. Sem argumento ele usa o padrão local-simulation (sobe um SuperLink local efêmero), por isso pode listar vazio se o seu run foi no deployment.

    Configuração e federações¶

    A config de conexão fica em .flwr/config.toml (lido via FLWR_HOME), não mais no pyproject.toml.

    flwr config list           # lista as conexões de SuperLink (federações)
flwr federation ls         # lista as federações (alias de federation list)
flwr federation simulation-config --num-supernodes 100   # config de simulação permanente
flwr federation create ...  # cria uma federação

    FLWR_HOME¶

    O Flower guarda a config dele (entre ela, o config.toml com as federações) numa pasta "casa". O FLWR_HOME é a variável de ambiente que diz qual pasta é essa.

    • Padrão: ~/.flwr, na home do usuário (C:\Users\<voce>\.flwr). Fica fora do projeto e não vai pro Git.
    • No Fleven: apontamos para a pasta .flwr dentro do projeto, que é versionada. Assim a config das federações viaja junto com o repositório, e um clone novo já vem com tudo.
    $env:FLWR_HOME = "$PWD\.flwr"   # estando na raiz do projeto
    • $PWD é a pasta atual do terminal — se rodar de outro lugar, aponta para o .flwr errado.
    • Vale só para a sessão atual do terminal (some ao fechar).

    No fluxo de experimentos você não precisa pensar nisso

    Só o flwr run . puro exige setar o FLWR_HOME. O fleven run e o tools/run_experiments.py já o definem automaticamente (apontando para a .flwr do projeto).

    Flower deployment¶

    Servidor e clientes rodam como processos separados. Suba o SuperLink, depois os SuperNodes, e então flwr run . <federação>.

    # Servidor
flower-superlink --insecure

# Cliente (um por nó, mudando partition-id)
flower-supernode --insecure --superlink <IP>:9092 \
  --clientappio-api-address 0.0.0.0:9094 \
  --node-config "partition-id=0"

# Rodar a federação
flwr run . fleven-deployment --stream

    # Servidor com TLS
flower-superlink \
  --ssl-ca-certfile certificates/ca-cert.pem \
  --ssl-certfile certificates/server-cert.pem \
  --ssl-keyfile certificates/server-key.pem

# Cliente valida o servidor pela CA
flower-supernode --root-certificates certificates/ca-cert.pem \
  --superlink <IP>:9092 --node-config "partition-id=0"

flwr run . fleven-deployment-tls --stream
    Flags úteis do flower-superlink
    • --database <arquivo> — persiste o estado dos runs entre reinícios (o padrão é em memória, some ao parar o SuperLink).
    • --enable-supernode-auth — liga a autenticação de nó.
    • --appio-ssl-* — certificado próprio para a ServerAppIo API, separado da Fleet API (recomendado em produção; TLS por serviço).
    Autenticação de nó (produção)

    A partir da 1.23 o CSV estático (--auth-list-public-keys) foi deprecado; o cadastro é dinâmico via CLI, sem reiniciar o servidor. O SuperLink precisa subir com --enable-supernode-auth.

    flwr supernode register keys/cred.pub fleven-deployment   # cadastra pela chave pública -> cria node-id
flwr supernode unregister <node-id> fleven-deployment     # remove pelo node-id
flwr supernode list fleven-deployment                     # lista (alias ls; aceita --verbose)
flwr federation add-supernode <node-id> <federação> fleven-deployment  # associa nó já registrado
    • A chave pública deve ser P-384 (ou outra curva EC NIST).
    • O register recebe o arquivo da chave pública e cria o node-id; unregister/add-supernode recebem o node-id.
    • O último argumento é sempre o nome da conexão do SuperLink.
    • No carro, o SuperNode sobe com a chave privada via --auth-supernode-private-key (o --auth-supernode-public-key está deprecado na 1.31).
    Empacotar e distribuir o app (FAB)

    O Flower distribui a aplicação como um FAB (Flower App Bundle). No flwr run o FAB é montado e enviado automaticamente; estes comandos servem para inspecionar/gerenciar a distribuição.

    flwr build              # empacota o app atual num FAB (ou flwr build --app <path>)
flwr install ./app.fab  # instala um FAB localmente (vai para $FLWR_HOME/apps/)

    Conta e Flower Hub (não usados no Fleven): flwr login <superlink> autentica numa SuperLink protegida por conta; flwr app publish/flwr app review publicam e revisam apps no Flower Hub (a plataforma hospedada do Flower). Como o Fleven é self-hosted por privacidade, esses não entram no fluxo — a autenticação de nó funciona sem login nem Hub.

    Variáveis de ambiente¶

    Variável O que faz
    FLWR_HOME Onde o Flower lê a config das federações ($env:FLWR_HOME = "$PWD\.flwr")
    PYTHONUTF8 Evita erro de encoding (emojis do Flower) no Windows ($env:PYTHONUTF8 = 1)
    DAGSHUB_USER / DAGSHUB_TOKEN Credenciais do fleven push
    MLFLOW_TRACKING_USERNAME / _PASSWORD Auth do MLflow remoto — definido automaticamente pelo fleven push a partir das DAGSHUB_*
