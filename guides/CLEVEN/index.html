    CLEVEN¶

    O que é¶

    O cleven é a bancada centralizada do Fleven: um pacote irmão (cleven/, entry point cleven) que treina um modelo por grupo de veículos (G01 a G05), concatenando as janelas de todos os clientes do grupo num único conjunto de treino, em vez de treinar de forma federada. O objetivo é descobrir quais modelos, features, hiperparâmetros e janelamentos tornam a previsão de energia por quilômetro aprendível, antes de voltar ao Fleven federado com uma configuração já filtrada.

    O cleven reusa o pipeline de dados do fleven (build_dataloaders, o mesmo DataContract, o mesmo StandardScaler por cliente) e o mesmo MLflowTracker de registro, então os experimentos aparecem lado a lado com os runs federados no MLflow, só que em experimentos cleven_{grupo} separados dos {grupo}_{model_type}_{strategy} do federado.

    Fluxo de uso¶

    # 1. Calibrar o custo antes de soltar a grade inteira (não toca em dados nem treina nada)
cleven sweep --only G05 --dry-run

# 2. Rodar a grade de verdade, só com validação
cleven sweep --only G05

# 3. Ver o ranking dos runs do grupo, ordenado por val/r2 (pooled, default)
cleven report -g G05
cleven report -g G05 --order-by r2_mean   # ranking menos otimista, ver abaixo
cleven report -g G05 -c cleven/sweeps/baseline.toml   # lê a tracking_uri do TOML

# 4. Avaliação única no teste, para a config vencedora
cleven final --config-hash <hash>
cleven final --config-hash <hash> --force   # só para re-execução legítima, ver protocolo

    <hash> é o config_hash impresso pelo --dry-run (ou visível na coluna hash de cleven report): um md5 de 12 caracteres sobre a configuração achatada (grupo, contrato, janela, hiperparâmetros de treino), usado tanto para nomear o run no MLflow quanto para o dedup de cleven sweep.

    Protocolo: seleção por validação, teste só no final¶

    A seleção de hiperparâmetros (cleven sweep) usa validação, nunca o conjunto de teste. O teste só é construído e avaliado por cleven final, uma única vez, para a config já escolhida.

    Trava de uso único do final: o cleven final recusa rodar quando o grupo já tem um run FINISHED com a métrica test/r2 gravada no experimento cleven_{grupo}, e sai com código 1 explicando o motivo. A razão é que rodar final várias vezes, com hashes diferentes ou não, permitiria escolher o melhor resultado de teste entre tentativas, que é exatamente a forma de vazamento que separar validação de teste existe para impedir. Para a re-execução legítima (correção de bug, contrato novo, mudança de pipeline) use --force: o comando então apenas avisa e prossegue. A checagem é fail-open, ou seja, se o MLflow estiver indisponível o comando roda com aviso em vez de travar o trabalho.

    Validação¶

    A validação sai de viagens inteiras, cortadas antes de qualquer coisa tocar o pipeline do fleven: cleven/source.py::TrainPoolSource embrulha a fonte real (EvedTripSource) e esconde as viagens de validação de read_trips, usando o mesmo _stratified_split que separa treino/teste (ordena por consumo médio e distribui uniformemente, para cobrir regimes baixo/médio/alto). build_dataloaders (o pipeline compartilhado com o federado, sem nenhum código de validação) só enxerga o que sobra - o scaler é ajustado sobre isso, então a validação fica fora do fit por construção, não por um cuidado manual em cada chamada. load_group recupera as viagens escondidas (source.val_trips, um método extra fora do Protocol TripSource - só o cleven chama) e as janela por conta própria, reusando o scaler que build_dataloaders devolveu. As janelas são geradas com non_overlapping=True: o contexto de uma começa onde o rótulo da anterior terminou, então nenhum rótulo compartilha leituras com outro.

    Mudança de semântica (2026-08-11, mover a validação para o cleven): antes, val_fraction era fração das viagens de treino (o corte vinha depois do split treino/teste, dentro do pipeline). Agora é fração de todas as viagens, porque o corte acontece antes do pipeline, e é o pipeline quem faz o split treino/teste sobre o que sobrou. Com train_test_split = 0.7 e val_fraction = 0.15, a divisão passa de 59,5%/10,5%/30% para 59,5% treino / 15% validação / 25,5% teste. Números de val_fraction de runs anteriores a esta data não são comparáveis - a fração nominal é a mesma, mas o denominador mudou.

    Um cliente só cede viagem para a validação se, depois do corte candidato, sobrarem pelo menos 3 viagens no pool (treino+teste) e pelo menos 1 na validação; abaixo disso o corte é descartado e o cliente contribui só com o pool inteiro, sem ceder nenhuma validação. O limiar do pool é 3, não 2, porque o pool ainda vai ser dividido em treino/teste PELO PIPELINE (train_test_split típico 0.7): com pool=2, int(2*0.7)=1 deixaria uma única viagem de treino, que nos parâmetros de produção (sequence_length=100, prediction_distance_km=0.5) não rende nenhuma janela — é o caso real do client_4 do G05 (3 viagens totais), que motivou a correção. Com pool=3, int(3*0.7)=2 sobra para treino, o mesmo que o cliente teria sem nenhuma validação. Não é um limiar fixo arbitrário: para val_fraction grande, um limiar pequeno demais deixaria o pool com 1 viagem só de qualquer forma, então TrainPoolSource faz o split candidato e CONFERE o resultado, em vez de tentar prever de antemão se vai dar certo. load_group reporta (clientes_sem_validacao) quais clientes ficaram de fora.

    val_decimate foi removido em 2026-08-10. Ele mantinha 1 janela a cada N para compensar a sobreposição da validação antiga, que era recortada da cauda das janelas de treino. Com o split por viagem não há o que decimar. Runs gravados antes dessa data não são comparáveis com os novos.

    Modo varredura não expõe o teste: load_group(..., with_test=False) (o modo usado por cleven sweep) nunca inclui X_test/y_test/idx_test no GroupDataset retornado - a seleção de hiperparâmetros não tem como alcançá-los, mesmo por engano. Isso é uma garantia de inalcançabilidade, não de não-cálculo: build_dataloaders (do fleven.data.pipeline, compartilhado com o federado) não tem parâmetro para pular o cálculo das janelas de teste, então ele sempre as monta internamente; cleven simplesmente as descarta antes de devolver o GroupDataset. É desperdício de CPU conhecido e aceito, não um risco de vazamento.

    Métricas¶

    Todas em unidade física (Wh/km, ou a unidade do target do contrato), invertidas janela a janela pelo StandardScaler do cliente de origem - cada cliente tem seu próprio scaler, então não dá para inverter em bloco.

    cleven/metrics.py (summarize) calcula, sobre o conjunto de validação (ou de teste, no final):

    • R² pooled: sobre todas as janelas de todos os clientes juntas, como se fossem uma amostra só.
    • R² médio: média simples do R² por cliente (todo cliente pesa igual, independente de quantas janelas tem).
    • R² ponderado: média do R² por cliente, ponderada pelo número de janelas (n) de cada cliente.
    • RMSE, MAE, Pearson: pooled, mesma lógica do R² pooled.
    • N efetivo (effective_n): tamanho amostral corrigido pela autocorrelação AR(1) da série, N_eff = N·(1-r)/(1+r), onde r é a correlação lag-1 medida sobre a sequência inteira do cliente (aproximação: cruza fronteiras de trip). N_eff tem teto em N (nunca reporta mais amostras efetivas que reais) e cai para N quando a série é curta demais, constante, ou r é numericamente instável perto de -1.

    Qual métrica usar para escolher o vencedor (cleven report --order-by): cleven report ordena por val_r2 (pooled) por padrão, mas exibe também val_r2_mean e val_r2_w como colunas, e aceita --order-by {r2, r2_mean, r2_weighted} para reordenar por qualquer uma delas. As três divergem porque, em unidade física, cada cliente tem uma média de alvo diferente (veículos diferentes consomem energia por km em faixas diferentes); no R² pooled, a variância ENTRE veículos entra no mesmo denominador que a variância dentro de cada veículo, então um modelo que aprende a diferença de escala entre carros (sem prever nenhuma dinâmica de verdade) já pontua bem - o R² pooled infla. val_r2_mean (média simples do R² por cliente, todo cliente pesa igual) e val_r2_w (média ponderada por n de janelas) medem, cada uma à sua forma, se o modelo prevê dentro de cada veículo, não só entre veículos. Um caso medido pelo revisor com dois clientes de escalas 1x e 2x: val_r2 pooled 0.470 contra r2_mean de -0.057 - o modelo parecia bom só porque acertava "qual carro é mais caro", não a dinâmica dentro de cada um. Recomendação: use val_r2 (default) para uma primeira triagem rápida, mas confirme o vencedor por r2_mean (o mais conservador, não deixa clientes com mais janelas dominarem) antes de rodar cleven final - se as duas ordenações discordam muito, é sinal de que o modelo está aprendendo a distinguir veículos em vez de prever a série.

    Por que o N nominal engana: janelas vizinhas cobrem quilômetros consecutivos da mesma trip, então são fortemente correlacionadas - não são N observações independentes. Numa auditoria manual dos parquets do G01 feita antes da implementação (não reproduzida por nenhum script do repositório; ver método abaixo), das 1049 janelas nominais do conjunto de teste o N_eff agregado ficava em torno de 594 - quase metade da "amostra" nominal era redundância, não informação nova. Em alguns clientes o R² individual estava apoiado em apenas ~12 amostras efetivas, mesmo com centenas de janelas nominais - um R² calculado sobre isso não é confiável por cliente, por mais que pareça sólido olhando só o n.

    Método da auditoria (para reproduzir): a fração de NaN foi contada por trip sobre as colunas obrigatórias do contrato mais o alvo (Energy_Consumption); uma trip cujas linhas são 100% NaN nessas colunas não sobrevive à limpeza e não produz nenhuma janela. A correlação usada no N_eff é a lag-1 entre os rótulos de janelas vizinhas dentro do mesmo cliente (mesmo cálculo de effective_n em cleven/metrics.py), e o N_eff em si é a correção AR(1) N·(1-r)/(1+r) aplicada sobre essas janelas. Os números acima (594 agregado, ~12 no pior cliente) vêm dessa contagem manual, não de um artefato salvo no repositório.

    Onde conferir o n_eff por cliente: nem cleven report nem cleven final mostram n/n_eff por cliente na saída de terminal. cleven report lista só métricas agregadas do run (val_r2, val_r2_mean, val_r2_w, val_rmse), uma linha por run e não por cliente; cleven final imprime n (sem n_eff) na linha de validação, e n/n_eff_total (a soma agregada, não por cliente) na linha de teste. O n e o n_eff por cliente são calculados e registrados, mas só chegam ao MLflow: val/client_N/n e val/client_N/n_eff (e, no modo final, test/client_N/n e test/client_N/n_eff) - ver _logar em cleven/experiment.py. Para ler o R² de um cliente com confiança é preciso abrir essas métricas no MLflow; a saída resumida dos comandos não substitui essa conferência, especialmente em grupos com poucos clientes ou trips curtas, onde o n_eff por cliente pode ser bem menor que sugere a saída agregada.

    Trips 100% NaN reduzem ainda mais o dado útil disponível, bem abaixo do que o número de trips alocadas sugere: na mesma auditoria do G01, 77 das 397 trips alocadas ao conjunto de teste não produzem nenhuma janela (todas as linhas descartadas antes do janelamento, pelo mesmo critério de NaN acima), e o cliente 3 sozinho perde 94 de suas 150 trips. O n/n_eff (agregados na saída dos comandos, por cliente no MLflow) já refletem essa perda - é o motivo de sempre olhar as métricas realizadas, não o inventário nominal de trips, para saber quanto dado um cliente de fato contribuiu.

    Comportamento de saída do cleven sweep¶

    • cleven sweep sai com código 1 se qualquer experimento da grade rodou e levantou exceção (resultado.falhas não vazio). Um --dry-run nunca roda nada, então nunca tem falhas e sempre sai com código 0.
    • Falhas na checagem de dedup (already_done, ex.: MLflow indisponível, tracking URI incorreta) são tratadas como fail-open: o experimento roda de novo, avisado no stdout e registrado em resultado.checagens_dedup_falhas (lista estruturada, não só log). Essas falhas não alteram o código de saída - o fail-open é deliberado, o pior caso é um rerun redundante, não um dado incorreto, então não é tratado como falha de experimento.
    • Configs puladas por dedup (already_done retornou True) não aparecem nem em sucesso nem em .falhas.

    Eixo weight_decay¶

    O TrainConfig do cleven expõe weight_decay (default 0.0), repassado até fleven.core.utils.train. O eixo funciona: train usa torch.optim.AdamW nos dois ramos de treino (parâmetros únicos e param groups do FedPer), com o weight_decay passado diretamente ao otimizador. Com o default 0.0, o comportamento é idêntico bit a bit ao Adam anterior (verificado numericamente) - nenhum run federado ou centralizado já registrado muda de resultado.

    A escolha foi AdamW, não Adam com penalidade L2 acoplada ao gradiente: no Adam, a penalidade L2 entra somada ao gradiente e passa pela normalização adaptativa do otimizador, então pesos com gradiente histórico grande acabam recebendo menos decaimento efetivo - o oposto do que se pretende ao pedir mais regularização. O AdamW aplica o decaimento direto no peso, desacoplado do gradiente, então o efeito de weight_decay > 0 é previsível independente da escala do gradiente de cada parâmetro.

    Limitações¶

    1. O baseline herda personalização por scaler. Reusar build_dataloaders mantém a normalização por cliente (um StandardScaler por veículo), então o modelo centralizado já vê features calibradas por veículo - não é um centralizado "cru", sem nenhuma forma de personalização. Medir o efeito de um scaler único por grupo é um eixo futuro, fora do escopo atual.
    2. O cache do pipeline é invalidado ao varrer eixos de janela. A chave do cache (_cache/client_N_<hash>.npz) inclui a configuração de janelamento, então varrer sequence_length ou prediction_distance_km invalida o cache e reprocessa os parquets a cada combinação nova. Varrer eixos de modelo e de treino (tipo de modelo, learning rate, hidden size) é barato - reaproveita o cache. Por isso cleven sweep ordena a grade agrupando por (grupo, contrato, janela), para que as combinações que compartilham janela rodem em sequência.
    3. Trips 100% NaN reduzem o dado útil bem abaixo do número de trips. Ver a seção de métricas acima: no G01, 77 de 397 trips do teste não produzem nenhuma janela, e o cliente 3 perde 94 de 150 trips.

    Grade padrão (cleven/sweeps/baseline.toml)¶

    A grade em cleven/sweeps/baseline.toml varia train.model_type (lstm, lstm_dense, mlp), train.learning_rate (0.001, 0.0005) e train.hidden_size (64, 128) - 12 combinações - sobre os grupos G01 a G05, com janela e demais hiperparâmetros de treino fixos em [defaults]. Isso dá 12 experimentos por grupo e 60 no total. model_type = "fedper" não é aceito pelo cleven (build_model rejeita explicitamente): a cauda pessoal do FedPer só faz sentido em esquema federado, onde ela nunca sai do cliente.
