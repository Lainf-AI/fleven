    Contratos de dados¶

    O que é e por que existe¶

    Um contrato é um arquivo TOML que declara quais colunas entram no modelo, em que ordem, quais são obrigatórias e o que é o alvo. Ele é a fonte única da verdade sobre a forma da entrada.

    Isso importa porque o Fleven é federado. O servidor cria o modelo global e cada cliente cria o seu; se os dois discordarem sobre a largura do tensor de entrada, a agregação corrompe os pesos em silêncio. Em vez de repetir a lista de features em dois lugares e torcer para não divergirem, ambos derivam a forma do mesmo contrato, e comparam um resumo dele antes de trocar parâmetros.

    O contrato é indicado pela chave data-contract em pyproject.toml:

    [tool.flwr.app.config]
data-contract = "contracts/eved_potencia_rota.toml"

    Onde o arquivo é procurado¶

    _resolve_contract_path tenta, nesta ordem:

    1. caminho absoluto, se for absoluto;
    2. relativo ao diretório de trabalho, que cobre simulação e flwr run a partir da raiz;
    3. relativo à raiz do projeto, calculada a partir da localização do pacote fleven.

    O terceiro caso existe por causa do deployment: no SuperNode o ClientApp roda a partir do FAB extraído ou da imagem Docker, e o diretório de trabalho não é garantidamente a raiz. Se não achar em lugar nenhum, levanta FileNotFoundError dizendo onde procurou.

    Anatomia de um contrato¶

    schema_version = "1.0"
target = "Energy_Consumption"
use_feature_mask = false
route_grid_m = 25.0            # só relevante se houver features de rota

[[feature]]
name = "Vehicle Speed[km/h]"
unit = "km/h"
range = [0, 220]
required = true

[[feature]]
name = "MAF[g/sec]"
unit = "g/sec"
range = [0, 655]
required = true

[[route_feature]]
name = "Speed Limit[km/h]"
aggregation = "mean"

    Campos de topo¶

    Campo Default O que faz
    schema_version obrigatório Versão do formato. Hoje só "1.0" é aceita
    target obrigatório Coluna a prever
    use_feature_mask false Liga o canal de máscara (ver abaixo)
    route_grid_m 25.0 Passo da grade de distância das features de rota, em metros. Em route_mode = "profile" isso não é só escala: determina P, a forma da entrada de rota do modelo (ver abaixo). Contratos com route_grid_m diferentes produzem modelos com route_shape incompatível na mesma federação.
    route_mode "statistics" "statistics": cada [[route_feature]] (par coluna+agregação) vira um número. "profile": cada coluna distinta vira P pontos da grade de distância, preservando a ordem espacial do trecho em vez de resumi-la numa média.
    target_kind não "value" (padrão) ou "rate". Com "rate" o alvo é uma taxa instantânea (ex.: potência em kW) e o rótulo passa a ser a integral trapezoidal no tempo, em vez da soma dos valores.
    trip_gap_split_s não Segundos. Um intervalo maior que este entre leituras consecutivas encerra o segmento; janelas nunca atravessam o buraco. Ausente = não corta. Recomendado 60,0 para o eVED.

    [[feature]] — sinais lidos do passado¶

    Cada bloco declara uma coluna que o modelo lê ao longo da janela de contexto.

    • name: nome exato da coluna no parquet.
    • required (default true): se true, linhas com NaN nessa coluna são descartadas antes do janelamento. Se false, a linha sobrevive e a célula ausente é imputada.
    • range (opcional): [min, max]. É aplicado, não é documentação. clip_to_ranges grampeia valores fora da faixa antes de ajustar o scaler e janelar, protegendo o treino de glitches de sensor, como um RPM de 65535 vindo de um frame CAN perdido. NaN é preservado, o total grampeado é logado por feature, e uma feature sem range fica intocada. O range é opt-in.
    • unit e description (opcionais): documentação. Nenhuma conversão de unidade é feita.

    A ordem dos blocos importa. Ela define a ordem das colunas no tensor e entra no fingerprint.

    O alvo¶

    O target pode ser qualquer coluna materializada no parquet, não só Energy_Consumption, que é apenas o default do eVED. Para prever outra grandeza, aponte target para ela.

    Duas restrições. O alvo não pode também estar declarado como feature, porque ele já entra no tensor como coluna autorregressiva. E ele precisa estar materializado: derivar o alvo a partir de sinais crus é responsabilidade de quem coleta, não do framework.

    O canal de máscara¶

    Com use_feature_mask = true, o tensor ganha uma coluna binária por feature, indicando se aquela célula estava presente. Serve para frotas heterogêneas, onde alguns veículos não reportam certos sensores: o modelo passa a distinguir "valor ausente" de "valor igual à média".

    Com a máscara desligada, uma célula ausente vira 0 no espaço normalizado, que é a média, ou seja, um valor neutro mas indistinguível de uma leitura real igual à média. No eVED a frota é homogênea, então o default é false.

    Features de rota¶

    São atributos do trecho de estrada que ainda será percorrido, e existem sob a premissa de que o condutor definiu o trajeto. Enquanto as features normais dizem como o veículo vinha se comportando, as de rota dizem por onde ele vai passar.

    [[route_feature]]
name = "Speed Limit[km/h]"
aggregation = "mean"

[[route_feature]]
name = "Elevation Smoothed[m]"
aggregation = "delta"

[[route_feature]]
name = "Elevation Smoothed[m]"
aggregation = "positive_sum"

    A identidade de uma feature de rota é o par coluna mais agregação, e não só a coluna. Por isso a altitude pode aparecer duas vezes, como desnível líquido e como subida acumulada, que são grandezas físicas diferentes.

    Agregações disponíveis¶

    Agregação O que calcula
    mean Média dos valores ao longo do trecho
    delta Valor no fim menos valor no começo
    positive_sum Soma apenas dos incrementos positivos

    A grade de distância, e por que ela não é um detalhe¶

    As agregações não são feitas sobre as leituras do trecho. A coluna é primeiro interpolada em pontos igualmente espaçados ao longo da distância, a cada route_grid_m metros, e a agregação roda sobre essa grade.

    O motivo é que o OBD amostra por tempo, uma leitura por segundo, não por distância. Agregar por leitura faria as features carregarem velocidade futura. Um exemplo com números: num trecho de 500 m, metade numa via de 40 km/h percorrida a 20 km/h (45 s, 45 leituras) e metade numa via de 90 km/h percorrida a 90 km/h (10 s, 10 leituras), a média por leitura dá 49,1 km/h e a média por distância dá 65,0 km/h. A primeira só vale 49,1 porque o motorista demorou na primeira metade, e essa diferença é invertível: o modelo deduziria o tempo gasto em cada parte, ou seja, exatamente a informação futura que ele não deve ter.

    Com a grade, as features passam a ser função da geometria do trajeto, iguais a 20 ou a 80 km/h. O número de pontos vem do horizonte nominal e do passo, nunca da amostragem: 500 m com passo de 25 m dão sempre 21 pontos.

    route_grid_m fica no contrato, não na configuração de execução, e isso é deliberado. Dois nós com resoluções diferentes produziriam features numericamente distintas com o mesmo input_size, e o handshake, que compara larguras, não pegaria a divergência. Estando no contrato, ele entra no fingerprint e a incompatibilidade é recusada na entrada.

    Restrições das features de rota¶

    O contrato recusa três coisas, e as três protegem a premissa da feature:

    1. Nomear o target. Agregar o alvo sobre o trecho futuro entregaria o próprio rótulo ao modelo.
    2. Nomear uma feature dinâmica já declarada. Sinais do veículo medidos no trecho futuro revelam como o trajeto foi percorrido. Features de rota devem ser atributos da via, não do comportamento do condutor.
    3. Combinar com prediction-mode = "steps". Nesse modo não existe trecho futuro com distância definida para agregar. A validação roda em load_contract, então servidor e cliente falham juntos na largada, e não com o servidor treinando sobre clientes que silenciosamente reportam zero exemplos.

    Comportamento com colunas ausentes¶

    Colunas de rota não entram no conjunto que provoca descarte de linha por NaN. Se a coluna não existe no parquet, ou o trecho não tem dados, o valor agregado vira neutro no espaço normalizado. Sem isso, acrescentar uma feature de rota passaria a matar viagens inteiras.

    Valores não numéricos são coeridos para NaN e a contagem é logada por coluna. Isso acontece de verdade no eVED: cerca de 1% das linhas trazem o limite de velocidade como faixa, no formato '40-48'.

    Como o input_size é derivado¶

    input_size = F + (F se máscara ligada) + 1

    onde F é o número de features. O +1 é a coluna autorregressiva do alvo. A rota não entra em input_size: ela é um tensor próprio, injetado uma vez no estado final da sequência em vez de replicado em todos os passos da janela.

    A ordem das colunas do tensor de sequência é:

    [ features escalonadas (F) ][ máscara (F, se ligada) ][ alvo (1) ]

    Quando o contrato declara [[route_feature]], o modelo recebe um segundo tensor, de forma (batch, P, R), dado por derive_route_shape(contract, prediction_distance_km):

    • Em route_mode = "statistics", P = 1 e R é o número de pares (coluna, agregação) — cada entrada de [[route_feature]] vira uma coluna.
    • Em route_mode = "profile", P vem da grade de distância (round(prediction_distance_km * 1000 / route_grid_m) + 1) e R é o número de colunas distintas citadas em [[route_feature]] (não o número de pares — em modo perfil o contrato recusa a mesma coluna duas vezes).

    Servidor e cliente chamam derive_input_size e derive_route_shape sobre o mesmo contrato, e passam ambos os valores a get_model (input_size e route_shape). Não defina input-size manualmente.

    O fingerprint e o handshake federado¶

    contract_fingerprint produz um hash de 16 caracteres cobrindo tudo que define a forma da entrada: schema_version, target, a flag de máscara, a sequência ordenada de features com seu required, a sequência ordenada dos pares de rota, o route_grid_m quando há rota, e o route_mode quando ele não é o padrão ("statistics").

    O servidor envia esse valor no config de cada mensagem de treino e avaliação. O cliente compara com o seu antes de participar; se divergir, ele se recusa e devolve num-examples=0, que é peso zero na agregação. Isso protege contra FAB misturado, override por nó e schema velho.

    Além do fingerprint, o handshake também confere o prediction-mode e, no modo por distância, o prediction-distance-km. Um servidor antigo que não envie handshake nenhum é tolerado, por compatibilidade.

    Duas propriedades que valem conhecer:

    • Contrato sem rota tem fingerprint idêntico ao de antes de a rota existir. Acrescentar o bloco de rota a um contrato que não o usa não muda o hash, então federações em execução não são invalidadas.
    • Mudar apenas o caminho do arquivo não muda o fingerprint. Ele descreve o conteúdo, não a origem.

    Validações¶

    O contrato é recusado quando:

    • schema_version é desconhecida;
    • falta target, ou não há nenhuma feature;
    • há nomes de feature duplicados;
    • o target também aparece como feature;
    • algum range tem mínimo maior que máximo;
    • uma agregação de rota é desconhecida;
    • um par coluna-agregação de rota está duplicado;
    • uma feature de rota nomeia o target ou uma feature já declarada;
    • há features de rota e route_grid_m não é positivo.

    O contrato implícito¶

    Se data-contract estiver vazio ou ausente, o framework monta um contrato a partir de feature-columns e target-column do run_config, com máscara desligada e todas as features obrigatórias. É um caminho de compatibilidade, útil para overrides pontuais via --run-config. Sem nenhum dos dois, usa as quatro features padrão do eVED e Energy_Consumption como alvo.

    O contrato em arquivo tem precedência e é o caminho recomendado.

    Criando um contrato novo¶

    Copie um dos existentes, ajuste, e aponte data-contract para ele. Confira o resultado antes de rodar:

    python -c "from fleven.data.contract import load_contract, derive_input_size, contract_fingerprint as fp; c = load_contract({'data-contract': 'contracts/meu.toml'}); print(derive_input_size(c), fp(c))"

    Três coisas a lembrar:

    Todos os nós precisam do mesmo contrato. Ele viaja dentro do FAB, construído na máquina do operador, então na prática isso é automático. O handshake existe para pegar os casos em que não é.

    Trocar de contrato invalida o cache. A chave do cache do pipeline inclui as features, o alvo, as features de rota e a resolução da grade, então o primeiro run com um contrato novo reprocessa os parquets.

    Para o G08, que é PHEV, o Energy_Consumption vem da bateria, não do MAF nem dos fuel trims. Um contrato para esse grupo deve usar HV Battery Current[A] e HV Battery Voltage[V] no lugar dos sinais de combustão.

    Erros comuns¶

    Mensagem O que aconteceu
    data-contract não encontrado O arquivo não está no CWD nem na raiz do projeto
    contrato divergente do servidor Fingerprints diferentes. Cliente e servidor com contratos distintos, ou FAB desatualizado num nó
    O target ... não pode também ser uma feature O alvo já entra como coluna autorregressiva; remova-o dos blocos [[feature]]
    Feature de rota ... não pode nomear uma feature dinâmica A coluna descreve o comportamento do condutor, não a via; agregá-la no futuro seria vazamento
    features de rota exigem prediction-mode='distance-energy' No modo steps não há trecho futuro com distância definida
    Cliente N sem janelas validas Features obrigatórias demais, ou cliente com muito NaN, ou viagens curtas demais para o horizonte. Considere required = false nos sensores intermitentes
    Cliente N sem coluna target 'X' A coluna do target não existe nos parquets daquele cliente
