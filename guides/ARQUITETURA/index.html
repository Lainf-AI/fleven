    Arquitetura: as três direções do projeto¶

    Este documento explica por que o Fleven está organizado como está. Os outros documentos explicam como operar cada peça: FEEDER.md é operacional, CONTRACTS.md é referência de schema, FLEVENCLIENT_PRODUCAO.md é o design do cliente embarcado. Aqui está o raciocínio que amarra os três.

    Convenção de status. Este documento descreve decisões de arquitetura, e nem todas já estão no código. Onde houver diferença, ela é marcada: [implementado], [planejado] com a tarefa que o entrega, ou [não existe]. Uma decisão registrada aqui sem marcação de status é raciocínio, não código.

    O problema de origem¶

    O produto final é aprendizado federado sobre dados de OBD que chegam em fluxo, gerados por veículos reais, em dispositivos que não estão sob nosso controle. Não temos essa frota. Não temos sequer um coletor embarcado rodando.

    Sem poder testar o caso real, restam duas opções ruins e uma boa. A primeira ruim é adiar: construir só o federado sobre dataset fixo e deixar a coleta para depois, o que garante uma reescrita quando o fluxo chegar. A segunda é adivinhar: projetar para um coletor hipotético e descobrir tarde que a hipótese era errada.

    A opção adotada foi terceira: separar o que dá para provar hoje do que só dá para provar com frota real, e construir a fronteira entre os dois antes de precisar dela. Daí saem as três direções.

    As três direções¶

    Cada direção prova uma coisa diferente. Confundi-las leva a exigir de uma o que só a outra pode dar.

    1. cleven, o baseline centralizado¶

    Escolhe modelo, features e janelamento sem o ruído da federação. Um modelo por grupo, todos os clientes juntos, seleção por validação, teste uma única vez.

    Prova: que existe sinal no dado e qual configuração o extrai melhor. Se o cleven não aprende, o federado também não vai, e o problema não é a federação.

    Não prova: nada sobre federação, privacidade ou heterogeneidade entre veículos.

    2. Experimentos federados (fleven run)¶

    Roda a grade grupo × modelo × estratégia sobre os dados já coletados do eVED, em simulação Ray. Métricas no MLflow, dedup por fingerprint de contrato.

    Prova: quanto custa federar. É a única direção onde dá para medir qualidade de modelo com rigor, porque exige dataset fixo, held-out reproduzível e comparação pareada. É também onde se compara FedAvg contra FedYogi, FedPer contra LSTM, e onde se mede se uma feature nova paga o próprio custo.

    Não prova: nada sobre fluxo de dados, coleta, finalização de viagem ou operação.

    3. Feeder e produção¶

    O feeder (tools/feeder/) reproduz viagens do eVED em wall-clock, respeitando a cadência real de Timestamp(ms), materializando trips uma a uma numa pasta que o ObdTripSource lê como se fossem viagens recém-finalizadas de um carro.

    Prova: que a arquitetura fecha. Que o dado chega em fluxo, que a viagem finaliza atomicamente, que o cliente treina sobre dado que cresce entre rounds, que o modelo federado serve inferência ao vivo, que o SuperNode autentica, que o FAB entrega o contrato certo.

    Não prova: acurácia. O dado é vivo e crescente por construção, então não há held-out estável nem cache reproduzível (obd.py devolve None em cache_root e trips_fingerprint de propósito). Medir R² aqui seria medir uma coisa que muda a cada leitura.

    Regra prática: uma feature nova se justifica nos experimentos; um mecanismo novo se justifica no feeder. Nunca o contrário.

    O eixo real: fonte de dados × modo de execução¶

    É tentador chamar isso de "modo de simulação" contra "modo de produção", mas são dois eixos independentes, e o Flower já distingue os dois.

    • Fonte de dados (data-source): eved (coletado, dataset fixo em disco) ou obd (fluxo, viagens que aparecem ao longo do tempo).
    • Modo de execução: simulação (Ray, um processo, atores) ou deployment (SuperLink + SuperNodes, processos ou máquinas separadas).

    Das quatro combinações, três se usam:

    simulação (Ray) deployment (SuperLink)
    eved (coletado) fleven run, a bancada de medição dados já coletados, um Pi por cliente
    obd (fluxo) não usável produção real, e o feeder no lugar do coletor

    A célula vazia é consequência do design, não omissão. O ObdTripSource resolve identidade por context.node_id (a identidade nativa do SuperNode, vinculada ao par de chaves EC registrado) e lê obd-data-path do run_config, que é compartilhado por todos os nós de uma simulação. Todos os clientes simulados leriam a mesma pasta. Fluxo pressupõe deployment, porque fluxo pressupõe que cada nó tenha o seu próprio dado local.

    Isso também mostra por que "rodar em dispositivos dos clientes" não é sinônimo de produção. Dá para fazer deployment real, com Raspberry Pis, sobre dados já coletados (célula superior direita). Isso testa rede, TLS, autenticação de nó e orquestração, sem tocar no problema de coleta.

    A camada fleven/data/¶

    Essa pasta existe para que a troca de fonte de dados não vaze para o resto do sistema. Ela contém:

    fleven/data/
├── contract.py   # DataContract, derive_input_size, contract_fingerprint
├── pipeline.py   # build_dataloaders: split, scaler, janelamento, cache
├── windows.py    # janelas deslizantes em NumPy, agnósticas de runtime
├── route.py      # agregação de features de rota numa grade de distância
├── source.py     # protocolo TripSource + registry
└── sources/
    ├── eved.py   # dataset coletado
    └── obd.py    # dado vivo/crescente

    TripSource: o adaptador de coletor¶

    O protocolo (source.py) é deliberadamente pequeno:

    class TripSource(Protocol):
    def list_clients(self) -> list[int]: ...
    def read_trips(self, client_id: int) -> list[pd.DataFrame]: ...
    def cache_root(self) -> Path | None: ...
    def resolve_client_id(self, context: Context) -> int: ...
    def trips_fingerprint(self, client_id: int) -> str | None: ...

    Cinco métodos, e cada um encapsula uma diferença real entre dataset e fluxo:

    • resolve_client_id separa seleção de dados de identidade. No eVED a partição é o índice do diretório (node_config["partition-id"]); no OBD os dados já são locais e o que importa é quem o nó é (context.node_id).
    • cache_root e trips_fingerprint deixam a fonte decidir se cachear faz sentido. Dataset fixo cacheia e valida por mtime+tamanho; dado crescente devolve None nos dois e sempre reprocessa, porque uma viagem nova precisa aparecer no round seguinte.
    • read_trips devolve DataFrames no schema que o contrato descreve. Esta é a responsabilidade que importa para a seção seguinte.

    O resto do sistema (pipeline.py, client.py, cleven) só conhece o protocolo. Trocar eved por obd é mudar uma string de config.

    O contrato¶

    O DataContract nasceu para um problema do federado, não do fluxo: o input_size precisa ser idêntico em todos os nós, senão a agregação de parâmetros não fecha. O contrato torna isso derivável (derive_input_size) e verificável (contract_fingerprint no handshake, com o cliente recusando participar se divergir).

    A segunda função veio depois e é a que interessa aqui: o contrato é também a especificação que o coletor tem que cumprir. Ele nomeia as colunas, as unidades, as faixas válidas e o alvo. Um coletor embarcado que produza trips conformes ao contrato é, por construção, compatível com a federação.

    A fronteira coletor / framework¶

    Esta é a decisão central, e a que motivou este documento.

    O framework não deriva grandezas físicas a partir de sinais brutos. O coletor materializa, o framework consome.

    O alvo é o caso que torna a regra concreta. Nenhum barramento OBD reporta potência ou energia consumida. O que chega são MAF, fuel trims, corrente e tensão de bateria, velocidade e timestamps. Alguém tem que aplicar a fórmula. Se esse alguém for o pipeline.py, três coisas quebram:

    1. O cliente embarcado passa a carregar colunas brutas que só existem para alimentar uma conta, engordando o payload e o schema do contrato.
    2. A fórmula fica presa ao framework, então um coletor de outro fabricante teria que entregar sinais brutos no formato que o nosso pipeline espera, em vez de entregar a grandeza acordada.
    3. O contrato deixa de descrever o dado e passa a descrever um cálculo, o que é uma fronteira muito pior de versionar.

    Quem materializa o alvo¶

    Uma fórmula canônica, em fleven/data/energy.py, com três chamadores previstos. Hoje existe um:

    caminho quem chama quando status
    eVED (fleven run, cleven) EvedTripSource.read_trips ao ler, em memória [implementado] sources/eved.py
    feeder (replay) DerivingCollector.process ao materializar a viagem [implementado] tools/feeder/collector.py
    produção OBD coletor embarcado ao finalizar a viagem [não existe]

    O pipeline.py não sabe da fórmula, e não pode saber: ele recebe DataFrames que já têm a coluna que o contrato nomeia. Essa é a regra que a fronteira existe para proteger.

    Por que o eVED é um caso especial¶

    Os parquets do eVED são a gravação de um coletor que já existiu: os notebooks originais do dataset, que materializaram a coluna Energy_Consumption. Do ponto de vista da arquitetura, aquele notebook era o coletor.

    O problema é que aquele coletor errou. A coluna Energy_Consumption guardada tem três defeitos medidos:

    1. Multiplica a taxa de queima pela velocidade instantânea, o que não está no Algoritmo 1 do artigo do VED. O valor guardado é a energia fisicamente correta multiplicada por v/127,65 (identidade exata, correlação 1,0000000000 medida no G05). Consequência: veículo parado com motor ligado tem alvo exatamente zero, em 15,7% das leituras (medido em G05/client_0, 60 viagens).
    2. Converte MAF de "galões" para litros multiplicando por 3,78541, mas MAF está em gramas por segundo. Faltava dividir pela densidade da gasolina. Erro constante, inofensivo isolado.
    3. Assume amostragem de 1 Hz nos dois ramos (combustão e bateria). O eVED tem mediana de 700 ms entre leituras, p1 de 100 ms e p99 de 2400 ms, com apenas 10,1% dos intervalos exatamente em 1000 ms. Ao somar por 0,5 km, isso distorce cada rótulo por um fator entre 0,56 e 1,01, CV de 13,8%.

    Além disso, para PHEV o ramo usado é só o da bateria, ignorando o combustível, e os clientes do G08 têm MAF a 100%, ou seja o lado do combustível está disponível e simplesmente não foi usado. Em G08/client_0, 46,4% das leituras com motor queimando têm alvo menor ou igual a zero. Em client_171, um PHEV que reporta Fuel Rate do OEM, são 82,8% das leituras com o motor comprovadamente ligado (6,04 L/h em média).

    Por isso o EvedTripSource assume o papel de coletor: ele aplica a fórmula canônica na leitura e entrega a coluna correta, sem tocar nos parquets. Os arquivos originais ficam intactos, Energy_Consumption continua existindo como artefato histórico, e os runs antigos do MLflow continuam reproduzíveis.

    A decisão de não escrever no disco tem três razões: não muta o dataset de origem, não duplica dezenas de GB, e principalmente mantém o paralelo com produção, onde também não existe uma etapa de reprocessamento em lote. Em produção o coletor calcula uma vez, ao fechar a viagem, e pronto.

    Semântica da coluna: taxa, não energia acumulada¶

    A coluna materializada guarda potência instantânea em kW [implementado], não energia já integrada por leitura. A integração de taxa × dt na construção do rótulo, pela regra do trapézio e simétrica com a integração de distância que já existe no pipeline.py, é [implementado]: quando target_kind = "rate", pipeline.py integra o alvo pela mesma quadratura usada para a distância, em vez de somar os valores crus.

    O motivo é de transferência entre coletores. Energia por leitura é propriedade do veículo e da cadência do logger. Decompondo a variância no G05, em log, 66,8% da variação de energia-por-leitura vem do dt e não do veículo (correlação de +0,761 com log dt, contra -0,086 para a taxa). Como a coluna do alvo também entra como entrada autorregressiva do modelo, isso significaria alimentar o LSTM com uma feature cuja maior fonte de variação é o jitter do logger. E um modelo treinado na cadência do eVED não transferiria para a cadência do coletor OBD.

    Taxa é invariante à cadência, é o que qualquer coletor consegue produzir de forma idêntica, e é interpretável quando o prediction-mode é steps (potência futura em kW).

    O feeder como coletor simulado¶

    Com a fronteira definida, o papel do feeder fica exato: ele é a implementação de referência do coletor, rodando sobre dados gravados em vez de sobre um barramento CAN.

    Ele faz parte do que o coletor embarcado vai fazer:

    • [implementado] lê pontos em cadência real, ponto a ponto (on_point), não em lote;
    • [implementado] materializa a trip atomicamente, com *.tmp durante a escrita, para que o ObdTripSource nunca leia um arquivo pela metade;
    • [implementado; integração pendente] consulta o contexto de rota por posição, via Valhalla, em vez de copiar as colunas de mapa que o eVED já traz; a conexão com uma instância real do serviço ainda não foi testada;
    • [implementado] calcula o alvo (materializar);
    • [implementado] separa transporte de coleta, com o DerivingCollector recusando rodar quando o contrato exige contexto e nenhum provedor foi configurado.

    Uma coisa que ele [não faz], e é importante não confundir: o feeder não decide onde uma viagem começa e termina. Ele itera sobre os arquivos trip_*.parquet que o eVED já delimitou e reproduz cada um. As fronteiras são herdadas do dataset, não decididas. Em produção essa decisão é do coletor, e é o assunto da seção seguinte.

    Quando o coletor real existir, ele substitui o feeder sem que nada acima dele mude. É por isso que o feeder vive em tools/ e não entra no FAB nem na imagem slim do cliente: ele é a peça que será trocada.

    Fronteira de viagem e buracos no fluxo¶

    Esta seção registra uma decisão que só faz sentido tomar quando o coletor embarcado for desenhado, e o raciocínio que a sustenta.

    O problema, no dado gravado¶

    Uma viagem do eVED pode ter buracos: leituras consecutivas separadas por minutos. O arquivo não sinaliza nada; são só duas linhas com timestamps distantes.

    O pipeline calcula distância integrando velocidade × tempo, então um buraco de 10 minutos a 50 km/h vira 8,3 km percorridos num único passo. Isso é ficção: ninguém sabe o que o veículo fez ali.

    O estrago concreto é no rótulo. Uma janela que encosta no buraco pergunta "ande até completar 0,5 km", o passo seguinte pula 8,3 km, e ela para ali. O rótulo então soma a energia de uma leitura, meio segundo de viagem, e é gravado como se fosse a energia de 0,5 km. Numa viagem sintética de teste:

    rótulo honesto (72 leituras) : 720
rótulo produzido (1 leitura) :  10     <- 72 vezes menor, e entra no treino como fato

    Essas janelas não deveriam existir. O segmento acabou, não há dado, não há como medir os próximos 0,5 km. O certo é descartá-las, que é o que aconteceria se o arquivo simplesmente terminasse ali, que é a verdade.

    trip_gap_split_s [implementado] faz esse descarte, cortando a viagem no buraco.

    Por que isso é conserto de dado de terceiro¶

    Em produção o buraco não deveria chegar ao arquivo. O coletor está ao vivo: ele sabe, no momento, que o fluxo parou e quando voltou. O comportamento certo é fechar a viagem quando o fluxo para e abrir outra quando volta. As leituras de antes viram a viagem N, as de depois a N+1. Nada se perde, exceto as janelas a cavalo do buraco, que não teriam rótulo possível de qualquer forma.

    Ou seja: em produção não existe "corte", porque não existe buraco dentro de uma viagem. As viagens nascem limpas. O campo do contrato existe porque o eVED foi gravado por outra pessoa, com outro critério, e herdamos os buracos prontos. Mantê-lo no pipeline é defesa em profundidade, para o caso de um coletor cair no meio de uma viagem e voltar.

    O critério certo não é duração, é o que o veículo estava fazendo¶

    Um limiar de tempo é proxy. O critério real é outro, e só o coletor tem acesso a ele:

    situação o que houve decisão certa
    parado no semáforo, start-stop desliga o motor barramento silencia por 40 s, o carro não saiu do lugar manter a viagem aberta: essa marcha lenta é parte do padrão de condução que queremos modelar, e o consumo ali é genuinamente perto de zero
    estacionou ignição desligada, minutos ou horas fechar a viagem
    perdeu o barramento andando adaptador soltou, ECU dormiu, processo caiu fechar a viagem: não sabemos o que houve naqueles segundos de condução

    O que decide é se o veículo estava em movimento e se a ignição foi desligada. O coletor sabe as duas coisas em tempo real; um dataset gravado, não.

    O limiar de 60 s funciona no eVED porque lá as duas populações coincidem quase perfeitamente com a duração:

    buracos de 10 a 60 s : 99,3% com o carro PARADO nas duas pontas, MAF médio 0,20
buracos acima de 60 s:  0,0% parado, velocidade média 84,6 km/h, MAF médio 13,21

    Abaixo de 60 s é o carro parado com o logger ocioso, e atravessar não inventa nada porque não havia nada acontecendo. Acima é o carro em rodovia com o registro falhando. A coincidência é do dataset, não um princípio: em produção, usar o proxy seria pior que usar o critério direto, que está disponível.

    Uma opção que só produção tem¶

    O coletor pode registrar a interrupção em vez de só partir a viagem: uma coluna marcando "aqui o fluxo caiu por N segundos" preserva a informação, e o pipeline decide o que fazer com ela. Fechar a viagem descarta o fato de que houve falha; um marcador não.

    [não existe], e é decisão para o desenho do coletor embarcado, não para agora.

    O que falta para produção¶

    • Coletor embarcado real, lendo do barramento OBD-II. O feeder define parte do contrato de comportamento que ele tem que cumprir, mas não todo: fronteira de viagem o feeder herda do eVED e não decide.
    • Política de fronteira de viagem, conforme a seção "Fronteira de viagem e buracos no fluxo": fechar por ignição desligada e por perda de barramento em movimento, não por limiar de tempo. Inclui decidir se a interrupção vira marcador no dado.
    • Alvo derivado de sinais realmente disponíveis no barramento. A fórmula canônica usa MAF, fuel trims, corrente e tensão de bateria. Nem todo veículo expõe todos; a coluna de qualidade materializada junto ao alvo registra quais termos entraram.
    • Registro operacional de nós. O mecanismo existe (flwr supernode register, chaves EC P-384, --enable-supernode-auth), falta o procedimento de frota.
    • Reprodutibilidade do scaler entre reinícios do cliente, apontada em FLEVENCLIENT_PRODUCAO.md.
    • Provedor de rota em produção. A interface considera um Valhalla local e identifica o extrato por --extract-version, mas ainda não passou por um teste de integração com o serviço real. Em campo, latência e disponibilidade também precisam ser tratadas.
    • Densidade de acidentes de via a partir do provedor, detalhado abaixo.

    Pendência específica: acidentes de via (cruzamento, travessia, ponto de ônibus)¶

    Estas features funcionam nos experimentos e NÃO funcionam em produção, e o motivo é a assimetria que este documento descreve: elas vêm de colunas que os autores do eVED juntaram do mapa, não do barramento.

    O que foi medido (G05, janelas de 0,5 km, correlação intra-cliente com Total Power[kW], contando eventos distintos e não leituras):

    variável correlação
    cruzamentos +0,2489
    travessias +0,1912
    pontos de ônibus +0,0815

    Para comparação, o limite de velocidade dá -0,2222 e o desnível +0,2181. Ou seja, cruzamento é competitivo com as features de rota que já usamos, e o mecanismo é o mais forte que medimos: parar custa 21,93 L/100km contra 5,61 em cruzeiro, um fator de 3,9.

    Duas armadilhas encontradas no caminho, e elas voltarão a aparecer para quem implementar isso a partir dos nós do Valhalla:

    1. Agregar o marcador cru pela grade de distância não funciona. No eVED a coluna é 1.0 onde há o acidente e NaN no resto; interpolada, ela vira NaN com zero ou um acidente e 1.0 constante com dois ou mais. Não distingue contagem alguma.
    2. Contar leituras marcadas vaza velocidade. O marcador dura 4 leituras em mediana, e o comprimento do evento correlaciona -0,35 com a velocidade: quem passa devagar pelo mesmo cruzamento gera mais leituras marcadas. A correlação medida cai de +0,2976 para +0,2489 ao trocar contagem de leituras por eventos distintos, e a diferença era vazamento.

    A solução para as duas é materializar o marcador como 0/1 e deixar a média sobre a grade de distância produzir uma densidade por distância. Verificado sinteticamente, mesma via a três cadências: 40 leituras dão densidade 0,0857, 120 dão 0,0952 e 400 dão 0,0952, enquanto a contagem crua de leituras marcadas vai de 3 para 32.

    Por que o código disso foi removido¶

    A implementação existiu (fleven/data/context.py mais o contrato contracts/eved_potencia_contexto.toml) e foi removida. O motivo não é que estivesse errada, e sim que a evidência ficou contrária em duas frentes:

    • Mediu pior. Acrescentar as três densidades ao contrato de rota piorou o R² em 8 de 9 configurações, delta médio -0,0446, cancelando quase todo o ganho de +0,0455 das features de rota.
    • A explicação que sustentava "remedir depois" foi refutada. A hipótese era que a culpa fosse a amostra efetiva, com janelas sobrepostas em 98%. A varredura de train_stride (2, 10, 25, 50, 100), com o conjunto de validação mantido constante via stride × decimate = 100, mostrou r2_pooled plano entre 0,4312 e 0,4387. Mais amostra independente não muda nada, então não havia conserto pendente esperando. (O mecanismo stride × decimate não existe mais: a validação, a partir de 2026-08-10, sai de viagens inteiras, separadas do treino e janeladas sem sobreposição — val_decimate foi removido. A conclusão acima continua valendo, é só o "como" que mudou; ver cleven/sweeps/stride.toml.)

    Guardar código sem consumidor e sem hipótese de melhora é dívida. O raciocínio, as armadilhas e os números ficam aqui; a implementação está no histórico do git.

    O que falta para produção. O ValhallaRouteProvider pede apenas atributos de aresta (edge.* em COLUNAS_DE_EDGE) mais a altitude. Cruzamento e semáforo são atributos de nó (node.* no trace_attributes), um caminho de código diferente: nó é um ponto no trajeto, aresta é um trecho, então a agregação por distância também muda. Enquanto isso não existir, um contrato com estas features não pode ser usado no fluxo OBD, e a materialização em context.py só cobre o caminho eVED.

    Resultado medido, e é negativo. Acrescentar as três densidades a um contrato que já tinha as três features de rota piorou o R² em 8 de 9 configurações, com delta médio de -0,0446, cancelando quase todo o ganho de +0,0455 que as features de rota tinham dado. Não é redundância: cruzamentos correlacionam apenas -0,18 com o limite de velocidade e -0,008 com o desnível, ou seja carregam sinal independente. É variância: ver a seção seguinte.

    Rota, contexto e o que não cabe no contrato¶

    Dois vocabulários se sobrepõem neste projeto e vale separá-los, porque a confusão já gerou um contrato mal nomeado (eved_potencia_contexto.toml, cujos blocos novos são, mecanicamente, apenas mais [[route_feature]]).

    [[route_feature]] é um mecanismo. Uma coluna agregada sobre o trecho à frente, numa grade de distância. [implementado] Não é mais replicada nos passos da janela: é um tensor próprio (batch, P, R), injetado uma vez no estado final da sequência, via RouteEncoder. Em route_mode = "statistics" (padrão) P = 1 e cada [[route_feature]] (par coluna+agregação) vira uma entrada — mecanicamente equivalente à agregação escalar de antes, só que fora da sequência em vez de repetida dentro dela. Em route_mode = "profile", P são os pontos da própria grade de distância e o modelo recebe o perfil, não o resumo: preserva a ordem espacial do trecho, que a média apaga (ver CONTRACTS.md). O contrato proíbe que ele nomeie o alvo ou uma feature dinâmica já declarada, porque um sinal do veículo medido no trecho futuro revela como o trajeto foi percorrido, e não a via.

    Contexto é uma procedência. Dado que não vem do barramento nem é calculado dos sensores: limite de velocidade, altitude, cruzamento, faixas, mas também temperatura ambiente e hora do dia.

    Contexto é mais amplo. Feature de rota é o subconjunto do contexto que descreve a via à frente e que dá para agregar sobre um trecho de distância definida.

    O que não tem como ser expresso hoje¶

    derive_input_size é F + (F se máscara) + 1; a rota não entra mais aí, é derive_route_shape que dá a forma (P, R) do tensor separado. Não existe conceito de escalar por janela que não venha do trecho à frente. Ficam de fora:

    variável por que não cabe
    temperatura ambiente é contexto, mas não é atributo da via à frente
    hora do dia é contexto, mas não é espacial
    tempo desde o início da viagem (motor frio) é estado do veículo, nem contexto é

    Expressá-las exigiria um bloco novo, algo como [[window_feature]]: um escalar por janela, calculado no instante do fim do contexto, sem agregação espacial.

    Por que isso NÃO foi implementado¶

    O motor frio é o mais tentador dos três: medimos +33% a +48% de consumo no primeiro minuto de viagem, efeito que some depois de ~2 minutos, e ele é derivável só do Timestamp(ms), sem serviço externo, idêntico em produção. Ainda assim, três medidas dizem para não implementar agora:

    1. Acrescentar features está saindo negativo. As densidades de acidente de via têm sinal independente e mesmo assim pioraram 8 de 9 configurações.
    2. O sinal já está na entrada. A janela de 100 leituras cobre 70,6 s em mediana (p10 48 s, p90 89 s), e o alvo entra como canal autorregressivo. Uma janela no início da viagem já contém as leituras de potência elevada do motor frio.
    3. A restrição que morde é amostra efetiva, não feature. Com train_stride=2 e janela de 100, as janelas se sobrepõem em 98%: as ~21 mil janelas de treino de um cliente equivalem a ~420 independentes. O val_loss sobe a partir da época 2, e uma regressão ridge sobre a média da janela chega perto do melhor LSTM da grade.

    A ordem correta é resolver a amostra efetiva primeiro (começando por train_stride) e só então reavaliar features. Implementar [[window_feature]] antes disso seria repetir o experimento que já saiu negativo, com um mecanismo novo para manter.
